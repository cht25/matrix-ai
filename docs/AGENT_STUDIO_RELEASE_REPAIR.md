# Agent Studio: persistent edits and immutable releases

## Diagnosed failure

The previous `stagePublishedFiles()` wrote the candidate to the *same deterministic Firestore document ID* as v1 (`published_sites/<slug>/files/pub_<hash(path)>`) and then iterated old documents, deleting every old document with a matching path. For the normal v2 case (`index.html`, CSS, JS at the same paths), this deleted the newly written v2 documents. Verification then requested the site and saw missing files. This is a deterministic source-level explanation for `DEPLOY_VERIFY_FAILED`; without access to production Firestore/logs, the exact HTTP status for the screenshot's v2 cannot be asserted. The old verifier also accepted unrelated stale HTML if it happened to contain a `<base>` tag.

## Storage and editing

Existing Firestore `projects/<id>/files` remains the source of truth, with transactionally incremented revisions, a file index, dependency references (from package.json, when present), static-hosting metadata and full source snapshots under `projects/<id>/versions`. `applyProjectFiles()` merges changed files, retaining unrelated files. Existing version list, source restore, deployment list, deployment logs and rollback APIs remain in place. The build resolves an explicitly owned project first, then an owned active conversation project, then a unique linked project, then a uniquely named owned project. An explicit “create another/new project” request overrides the client's automatically supplied current-project context. Ambiguous or unbound edit requests fail rather than creating/overwriting the wrong project. The conversation's `active_project_id` is persisted. The coding provider receives saved source, file index, revision and deployment slug on each turn; it is instructed to return only changed files. Omitted sensitive/oversized source cannot be silently overwritten.

## Release lifecycle

Each deployment now stages immutable files under `published_sites/<slug>/releases/<deploymentId>/files`, leaving legacy `/files` and the active `live_release_id` untouched. The public route uses the active release pointer, or the legacy collection for pre-upgrade sites. The verifier uses a new per-attempt secret header and unique query for its staged candidate; unauthenticated visitors keep seeing the old version. It checks the no-slash URL's relative redirect, the candidate HTML content (not just a `<base>` tag), and local assets, refusing external redirects and reporting bounded HTTP status/body details. After success, one site-document write switches the live pointer. On failure, the previous pointer/status is restored and candidate files are removed; the previous deployment and site remain intact. Rollback uses the same staged verification path. Deployment records retain version, source revision, staged/verified state, failure stage, safe diagnostic and timestamp. No old site IDs, owner IDs or existing files are deleted to migrate to this format.

## Environment and honest limits

`NEXT_PUBLIC_APP_URL` must be the TLS origin bound to this Next service. The server needs Firebase Admin credentials; frontend Firebase variables are public SDK configuration, not Admin credentials. Firestore rules deny client reads of published-site metadata (including the verifier's one-time token). Reverse proxies must forward `/s/*`, its query and `x-matrix-verification-token` to the Next server; a proxy that drops the header will yield a reported 404 during staged verification, not a false LIVE state. CDN caching must respect `private, no-store` on verification responses. Do not expose the Admin SDK key or other secrets in generated files or `env_public`.

MATRIX static hosting **does not install npm packages or compile arbitrary Vite/Next apps**. The stage formerly labelled “Installing dependencies” checks declarations; its UI now says so. Static HTML/CSS/JS is bundled/inlined and published. A real package runtime needs a separate isolated build/hosting provider, not a misleading success label. The project manifest records dependency references, not installed packages.

There are no production Firebase credentials or production site records in this checkout. Automated tests exercise transactional source edits, resolution, immutable stage/activation, relative redirect, asset fetching, stale-content rejection, timeout and write failure. A real authenticated two-project create/edit/deploy/rollback browser exercise and inspection of the screenshot's failed deployment ID require the operator's deployed environment and AI provider configuration. No production data was accessed or modified here.
