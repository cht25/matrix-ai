# Agent project identity and recovery

## Root cause

The old `resolveAgentProject` queried all `projects` tagged with a conversation and threw `PROJECT_AMBIGUOUS` when more than one was found, even when the user was simply requesting a new site. `ensureProject` independently returned the **first** project with that conversation ID. Since the browser sent its last `agentProjectId` as if it were an explicit user choice, creation in an existing Chat could reuse or overwrite the old project. Chats were only partially bound (`active_project_id`); missing bindings and legacy duplicate links produced contradictory choices. The build pipeline converted the error code into the generic stop message instead of presenting a selection.

## Resolution and persistence

`resolveProjectContext` validates owner/archival state and returns an explicit CREATE/EDIT mode, the selected project ID, and its source. Priority: explicitly selected/typed ID; explicit request to create a new independent site; open Workspace project; the current Chat's durable active project; unique legacy Chat link; unique full title reference among owned projects. A new artifact request creates a separate project; an edit with no target returns `PROJECT_CONTEXT_MISSING`, never an arbitrary project. Genuine multiple owned matches return `PROJECT_AMBIGUOUS` with owned candidate names. The Chat offers an owner-scoped project chooser, and Retry uses that explicit ID. Opening an empty Agent Workspace no longer creates a blank project implicitly; its Create project button does so deliberately. Old projects are not deleted or migrated destructively.

New first-project creation for an unbound Chat and binding of `conversations/{id}` to `projects/{id}` happen in a single Firestore transaction. Concurrent first builds reuse the committed project instead of creating duplicates. Subsequent explicit NEW requests get unique project IDs. Project file writes use the saved source revision as an optimistic concurrency precondition; stale writes fail with `PROJECT_REVISION_CONFLICT`. A failed CREATE retry reuses its persisted project ID. CREATE and EDIT log their mode and load the real project manifest, source files, revision, framework, entry point, build command and deployment pointer before generating modifications. Existing unrelated files and deployment records remain intact.

`conversations/{id}` stores `user_id`, `active_project_id`, `project_owner_id`, `active_source_revision`, `current_deployment_id`, `project_last_activity_at`, and `updated_at`. These are validated server-side against project ownership on binding and restored from the Chat document on reload. `projects/{id}` remains the authoritative owner/source/manifest/deployment record; `projects/{id}/files`, `projects/{id}/versions`, `build_runs`, `agent_tasks`, and `deployments` keep their existing histories. Multiple Chats may explicitly bind to the same project. Firestore's built-in single-field indexes cover the owner and legacy conversation queries; no new composite index or destructive migration is needed. The creation transaction enforces the existing per-user project limit.

## Production verification still required

This sandbox has no Firebase Admin credentials, emulator, actual records, or live Agent provider credentials. No production records were inspected or modified. After deploying the change, check a known affected account in Firestore (without deleting any duplicate records): verify conversation ownership and `active_project_id`, each linked project's `owner_id`/`conversation_id`, `revision`/`file_manifest` and `live_deployment_id`, plus associated deployment histories. Reopen its Chat, create two independent sites, edit each, retry a failed build, select between genuine ambiguous candidates, and confirm the actual published revision/URL. Client/Firestore integration and live deployment cannot be claimed from local tests alone.
