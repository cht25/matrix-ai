# Live Sites: proxy-safe routing

## Cause and repair

The Next.js application is proxied through a public HTTPS hostname to an internal Node port (reported as `localhost:10000`). `/s/<slug>` explicitly issued a 308 by cloning `req.nextUrl`, which can contain the **internal** upstream origin. Also, Next.js's default trailing-slash normalization can issue its own absolute redirect for `/s/<slug>/`, independently of the route. Either path could send a visitor to localhost.

`skipTrailingSlashRedirect` disables Next.js's implicit slash normalization. The public-site route now owns its root canonicalization with a **relative** `Location: /s/<slug>/` (including query string), so browsers remain on the public origin regardless of the trusted-proxy header settings. Do not make a public redirect from `req.url`, `req.nextUrl`, `Host` or `X-Forwarded-Host`. Render/Firebase must still forward the original host/protocol for other framework behavior and TLS; this redirect does not require trusting user-supplied forwarding headers. Other application routes are no longer automatically slash-normalized by Next.js.

The HTML response retains its site-scoped `<base href="/s/<slug>/">` so relative CSS/JS/images work after direct visits and nested navigation. Extensionless nested paths now fall back to the root `index.html` for client-side routers; missing assets still return 404. Static builds with root-absolute `/assets/...` references must be produced with a site-relative Vite base (`base: './'`) or relative references before publication; a `<base>` tag cannot change root-absolute references already embedded in a build.

The admin list constructs public links from the canonical configured `NEXT_PUBLIC_APP_URL` plus the **existing Firestore document ID**. Existing deployment records and generated URL entries are also resolved from their stored slugs, not their potentially stale stored localhost `public_url`. No migration, republish, document deletion or duplicate site creation is needed. Custom domains and private server-to-server addresses are not rewritten. HTTP publication verification tests both the actual no-slash Admin URL and the slash document URL. It accepts only a site-relative root redirect (or a direct success), rejecting any off-site/localhost redirect rather than recording it as live.

## Deployment / verification

1. Configure `NEXT_PUBLIC_APP_URL` to the actual HTTPS hostname bound to the deployment (e.g. `https://matrix.thamjj13.top`), and deploy this code to that service. Reverse proxy must forward `/s/*` unchanged to the Next.js server and pass the original Host / `X-Forwarded-Proto: https` for other routes. Do not proxy the browser to `localhost:10000`.
2. On the deployed service, inspect `curl -si https://<public-host>/s/<existing-slug>`: expect `308` and `Location: /s/<existing-slug>/` (not an absolute localhost URL). `curl -si https://<public-host>/s/<existing-slug>/` must return `200` with HTML; verify a nested SPA path and site-relative CSS, JS and images also return `200` with their correct MIME types.
3. Sign in as an admin, open Live Sites, inspect at least two existing links and open both in a fresh tab. Refresh, navigate nested routes, check network asset requests and verify unpublish for a site selected by the operator. Repeat a direct URL visit as a signed-out visitor.
4. If the production URL still redirects before reaching this handler, inspect the CDN/reverse-proxy rules and deployed revision. Redirects generated by an external proxy cannot be corrected solely by application code.

The checkout does not contain production Firebase credentials or the production site database. Local tests exercise legacy records and the public handler; a real audit of the ~10 production documents and authenticated/public browser checks require access to the deployed environment. No production records were modified here.
